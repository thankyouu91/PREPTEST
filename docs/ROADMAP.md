> **Go-live review, 2026-08-12.** The owner asked whether the platform is
> coherent and what it needs before running online. Findings below, in order,
> ahead of the rest of the queue: the first two were fixed on the spot, the
> remaining four are queued. Full write-up of the two fixes in `docs/SECURITY.md`
> §4. What the review found *healthy* is worth recording too, so nobody re-audits
> it: one runtime dependency and no npm advisories; server source, `.git`,
> `package.json` and `data/*.sqlite` all 404 over HTTP; no source maps and no
> secrets anywhere under `public/`; uploads sniffed by bytes with server-generated
> keys; OAuth checking state, nonce, issuer, audience and expiry with a
> timing-safe compare.

- [x] **Trust-proxy hole: the brute-force lockout could be walked straight past** — `app.set('trust proxy', true)` meant Express believed any `X-Forwarded-For` a client sent, and `req.ip` is what both the sign-in lockout and the global write limit key on. Demonstrated against a running server: five wrong passwords lock the `admin` account, but rotating the header meant the lock never engaged once — unlimited guessing. Now `TRUST_PROXY`, an integer defaulting to 0, where 0 means `req.ip` is the socket address and cannot be forged; `"true"` and any other non-integer resolve to 0 rather than being guessed at. Re-tested after the fix: 10 attempts from 10 different claimed addresses, locked from the sixth. Six unit checks plus two that read `server.js` itself, because a correct helper nobody calls protects nothing

- [x] **Student accounts from the admin side — create, grant a term, reset a password** (owner asked, 2026-08-13). Students self-register; a centre needs the opposite, and had no way to do it. `POST /admin/users`, `POST /admin/users/:id/grant`, `POST /admin/users/:id/password`, all behind the router-wide `requireAdmin` + `csrfGuard`
  - **The three terms are the three plans** — `starter-3m`, `plus-6m`, `pro-12m` — so nothing new was invented for "credits". The buttons are built from the price list the server publishes, which means a fourth plan appears by itself and a renamed one cannot go stale
  - A generated password is **shown exactly once**, with a copy button, and said plainly to be the only moment it is readable — the column holds a scrypt hash. Never logged
  - Created **verified**: an administrator typing the address in has confirmed it by other means, and leaving it unverified locks the person out of the account just made for them
  - A term runs from **today**, the same rule as a student redeeming a code. Extending from the current expiry would be kinder to renewals and would give the admin path different arithmetic from the student path — two answers to "when does this run out". Nothing is lost: `entitlementOf()` already takes the furthest date across live codes and adds the attempts up
  - Resetting a password **drops every session** that account holds. The reason for resetting is usually that somebody should not still be signed in
  - **`EMAIL_RE`, `passwordProblem` and `freeUsername` moved into `server/auth.js`.** There are now two ways an account comes into being, and two copies of "is this a valid password" is two rules that drift — the one that drifts being always the one nobody is looking at
  - `scripts/test-admin.mjs` 148 → 155 checks, and it now **drives the screen in a browser**: every control added here lives behind a modal, and a modal is what a screenshot pass never opens. The second-factor card sat unrendered by the gate for a whole turn for exactly that reason
- [x] **Cookies were not `Secure` in production unless a second switch was also set** — `NODE_ENV=production` alone left it off; it needed `FORCE_SECURE_COOKIE=1` as well. Two switches for one intention is how a deployment ships with session cookies a browser will send over plain HTTP while looking fully configured. Production now opts in by itself, and the env var survives as a deliberate override in both directions
- [x] **Mail delivery, and stop printing reset tokens to the log** — `server/mail.js`, two drivers behind one interface, the same shape as `server/storage.js`. `MAIL_DRIVER=console` (default) sends nothing and hands the link back to the caller outside production so the flow can still be clicked through; `MAIL_DRIVER=smtp` sends a real message. `scripts/test-mail.mjs`, 42 checks, wired into `npm run verify`
  - **The security half.** The token no longer reaches a log in any environment. Proved rather than asserted: registered an account against a server running `NODE_ENV=production` and counted `token=` across the whole log — zero. The test captures `console.log`/`console.error` around a real send and fails if the secret appears, while insisting the *recipient* still does, because a delivery nobody can trace to an account is its own kind of problem
  - **The SMTP driver is provider-agnostic, and that was a decision not an omission.** No mail account exists for this project, so choosing a provider's REST API now would have been guessing; SES, SendGrid, Postmark and Gmail-with-an-app-password all speak SMTP. Written against `node:net` + `node:tls`, so it holds the no-new-dependency line
  - **Tested against a fake SMTP server started on a loopback port**, which is the only honest way to check a hand-written protocol client with no mail account: it proves the actual conversation — EHLO, the multi-line 250- reply parser, AUTH PLAIN carrying the RFC 4616 NUL-separated triple, MAIL FROM, RCPT TO, DATA, the terminating dot — and that the bytes the server received are the message that was composed. What it deliberately does **not** prove is TLS negotiation against a real provider; that needs a real provider and is the one thing to check by hand on the first deploy
  - Three hardening points, each with its own check: a `\r` or `\n` in a recipient or subject is refused, because the address comes from the registration box and one newline is the sender writing their own `Bcc`; credentials are never sent over an unencrypted connection — no STARTTLS offered and not already TLS means AUTH is refused rather than downgraded, and the test confirms no `AUTH` command reached the wire at all; and the body is base64, so no line can begin with `.` and the dot-stuffing bug that catches hand-rolled SMTP clients is impossible rather than merely unlikely
  - Sending is not awaited. A slow mail server must not hold a registration request open, and a person who never gets the mail can ask again — the account exists either way
- [x] **Crash handling and a health endpoint** — `server/lifecycle.js` plus `GET /healthz`, with `scripts/test-health.mjs` (31 checks) in `npm run verify`
  - **Three separate problems, which is why the module has three parts.** A crash must be loud and final: both handlers log with context and exit **non-zero**, because a supervisor restarts on non-zero and leaves a zero alone — that exit code is the entire contract. A shutdown must be polite: `SIGTERM` is Cloud Run asking before a deploy, so it drains and exits **0**; without it every in-flight request is cut mid-response, which real people meet as a failed exam submission during a routine deploy. And either way it must be bounded: `server.close()` waits on open connections and an idle keep-alive waits for ever, so idle connections are closed at once and a timer (`SHUTDOWN_GRACE_MS`, 8s) guarantees the exit
  - **The worst state is not "crashed", it is "up and broken".** A process that swallows a fatal error keeps answering the health check, so nothing tells the platform to try again. That is the reasoning behind exiting rather than logging and carrying on, and it is written into the module rather than left implicit
  - **`/healthz` does a real database round-trip.** A handler answering 200 from memory reports "the process is up", which the platform can already see; what it cannot see is a process listening while its database has gone away. The endpoint says nothing else — no version, no path, no error text — because an unauthenticated endpoint volunteers nothing, and the reason a check failed belongs in the log where the operator is. Checked: one key in the body, and no path, database name or version string anywhere in it
  - **The lifecycle half is tested in child processes, and it had to be.** An exit code can only be observed honestly by letting a process exit; asserting on a mocked `process.exit` would test the mock. Seven child runs cover an unhandled rejection, an exception thrown from a timer (the case Express cannot catch, being off the request stack entirely), SIGTERM, SIGINT, a `close()` that never returns, and two signals racing. Then the real server was sent a real SIGTERM and logged its drain — the fake proves the logic, the real one proves the wiring
- [x] **Lockouts and rate limits moved out of process memory** — `throttle_locks` and `throttle_hits` in the database, behind the same seven functions, so not one call site changed. 12 new checks in `test-security.mjs` (59 to 71)
  - **It was wrong twice over, and only one of those was about scale.** A restart wiped every lockout, and `scripts/accounts.js` said so in as many words — 'bị chặn thì cứ khởi động lại server' — which is also the way out for whoever is doing the guessing. A counter that forgets helps the attacker more than the user. The scale half is the one the item named: on more than one instance the lockout silently became five attempts *per instance*, which would have undone the `TRUST_PROXY` fix at exactly the moment there was enough traffic to need it
  - **One row per hit, not a counter column.** A sliding window has to know *when* each hit landed, and `COUNT(*)` over a time range is race-free between processes in a way that read-modify-write on a shared row is not. `noteFailure` increments in a single `ON CONFLICT DO UPDATE`, so two processes cannot both read 4 and both write 5
  - **Proved by behaviour, not by storage.** 'It is in a table now' is a claim about where the data sits; the claim worth checking is that another process sees the same lock. The suite runs a real second process against the same database and asserts it does
  - Two smaller things fixed on the way past. `rateLimitPeek` could return 0 while the cap was reached, if the window had under a second left — and 0 means 'go ahead' to every caller, so a full bucket could read as an open door; it now floors at 1. And `accounts.js unlock` now clears both things called 'locked' — the administrator-disabled account *and* the wrong-password lockout — because clearing one and still being shut out by the other is a bad half-hour
  - The cost is a few indexed statements on every failed sign-in and every write request, which is the same order as the scrypt verification standing next to it. Measured across the whole gate: no step moved
  - **A consequence this item missed, found one turn later.** The suite signs in wrongly several times a run on purpose — that is how it proves a refused sign-in says the same thing whether or not the account exists. Five of those against one key is a 15-minute lockout, and now that the lockout is in the database it **accumulates between runs**: running the gate a few times inside a quarter of an hour turned a 401 into a 429 and took `test-user-api.mjs` from 59 to 58. Nothing was wrong with the code. `scripts/verify.sh` now clears `throttle_locks` and `throttle_hits` before starting the server, in the test database only — the same shape as the three env ceilings it already raises, and the same lesson: **a stateful anti-abuse mechanism has the test suite as one of its users**, so making one persist means checking who else was relying on it forgetting
- [x] **A fresh database shipped sixteen codes that opened nothing** — queued last turn as "`test-auth.mjs` cannot pass against a fresh database", which turned out to be the symptom rather than the fault. The suite was right and the product was wrong
  - **The bug.** `seed()` reconciles the demo codes' plans in a loop, and that loop sat about fifty lines ABOVE the INSERT that creates the codes. On a fresh database it ran while the table was still empty, found nothing to reconcile, and the INSERT below it names no `plan_id` column — so every demo code came out attached to no plan. Only the SECOND boot repaired them. Redeeming one answered *"This code has no plan attached. Ask your centre to issue a replacement"*, which is the sentence a new customer would have met on day one of a fresh deploy. Fixed by moving the reconcile below the insert, where a thing that repairs rows belongs relative to the thing that creates them
  - **It was a product bug, not a test bug.** Last turn's note said the gate "is green because of state a previous run left behind" and deliberately left the cause open. That was the right call: the state in question was the second boot, and the honest reading was that a fresh install was broken — not that the suite needed relaxing. A test that only passes on a database somebody else warmed up is a test telling you something
  - **The diagnosis nearly failed the same way the bug hides.** Requiring `server/db.js` runs the seed, so every `node -e` used to inspect the database was itself a second boot: I kept reading a repaired row and concluding the data was fine while the server disagreed. The `audit` table settled it — `user.redeem.noplan` was recorded — and the observation that finally held was made with a read-only `DatabaseSync` that never loads the seed at all. The regression check inherits that discipline: one process, one seed, one answer, in a database of its own
  - **The check was verified by putting the bug back.** Moving the reconcile above the insert again turns it red with "5 code(s) came out with no plan, so redeeming one would 409"; moving it back down turns it green. A regression test nobody has watched fail is a regression test nobody has tested
  - `test-auth.mjs` now passes 53/53 against a brand-new `PREP_DB`, and nothing in the suite was changed to make that true
- [x] **A second factor on the administrator sign-in** — TOTP (RFC 6238) in `server/totp.js`, enrolled from the command line, off by default. `scripts/test-totp.mjs`, 44 checks, in `npm run verify`
  - **TOTP rather than the IP allowlist the item also offered.** An allowlist is cheaper but blunt: it locks the owner out the first time a mobile network hands them a different address, and it protects nothing once somebody is on the same network. A second factor is the answer that keeps working
  - **Hand-written crypto is only acceptable because it is checked against the standard.** No dependency — HMAC-SHA1 is in `node:crypto` — and the suite runs the **six published RFC 6238 vectors**, including T=20000000000. That row is past 2³² seconds and is exactly the one that catches a counter written with a single `writeUInt32BE`, which is the classic way a hand-rolled TOTP passes every test anybody thought to write and then fails in 2106. "The HMAC looks right" is an opinion; agreeing with the standard on known inputs is what every authenticator app is built on

   — chín block đó đứng trước mọi mục khác trong mục này, không lấy vượt.
4. Chạy `npm run verify`. Đỏ thì sửa; không sửa được thì `git checkout -- .`, ghi lý do vào
   "Vướng mắc" bên dưới, commit riêng ghi chú đó rồi thoát. Không push code hỏng.
5. Với một block: qua đủ **sáu điều kiện khóa** (`docs/KE-HOACH-XAY.md` §1.2) rồi mới tick —
   cổng xanh, có test riêng **đã từng bị nhìn thấy đỏ** (ghi bằng chứng vào commit message),
   `node scripts/loadprobe.mjs` không tụt quá 15%, ảnh chụp mới, vẫn chỉ một dependency
   runtime, và một dòng trong `docs/BLOCKS.md`. Thiếu một điều kiện thì để nguyên 🟡
   "đang làm" và ghi lại còn thiếu gì — nửa block ghi là xong tệ hơn nửa block ghi là dở.
6. Tick ô đã xong, cập nhật README nếu có tính năng mới, commit và push.

Giới hạn: không đụng `data/` (dữ liệu chạy), không commit mật khẩu hay khoá bí mật, không
force-push, không tạo pull request, không đổi nhánh.
